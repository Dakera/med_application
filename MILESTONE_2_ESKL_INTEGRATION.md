# Milestone 2: интеграция eskl_unique.db как первичного источника данных о препаратах

## Контекст

До этого момента поток данных для получения ATC-кода препарата выглядел так:

```
Пользователь вводит препарат (RU)
  → TextMiningService.transliterate() — хрупкая эвристическая транслитерация RU→EN,
    надёжно работает только для substanceCanonical (2 препарата: эсциталопрам, сертралин)
  → AtcRepository.findAtcCodes(prefName) — JOIN по chembl_37.db (molecule_dictionary →
    molecule_atc_classification → atc_classification), только латиница
  → ATC-код + описание группы на английском
```

Проблема: транслитерация ненадёжна для произвольного ввода, а `chembl_37.db` не содержит
русских торговых названий вообще — из-за этого Autocomplete в UI по факту не работает
для препаратов вне захардкоженного списка.

## Решение

Появился новый asset — `eskl_unique.db`, собранный из официальной базы ЕСКЛП
(nsi.rosminzdrav.ru, "Лекарственные препараты. Товарные позиции"). Он даёт прямой путь
RU-название → ATC-код → русское название фармгруппы, без транслитерации:

```
Пользователь вводит препарат (RU: торговое название или МНН)
  → EsklRepository ищет по eskl_unique.db (name_trade / standard_inn)
  → сразу получаем code_atc + ftg_name_ru (RU) — готово, без похода в ChEMBL
```

**Архитектурное решение: `eskl_unique.db` становится первичным источником** для всего,
что связано с идентификацией препарата (автокомплит, ATC-код, фармгруппа).
`chembl_37.db` и `AtcRepository` переходят в статус вторичного/опционального источника —
не удаляем, но по умолчанию в основном потоке больше не используем.
`TextMiningService.transliterate()`/`substanceCanonical` тоже перестают быть частью
основного пути получения ATC-кода; используются (если вообще нужны) только для
сопоставления с внешними англоязычными источниками в будущем.

## Схема eskl_unique.db

Файл: `eskl_unique.db`, таблица `eskl_unique`, 21 563 строки, индексы на
`code_atc`, `name_trade`, `standard_inn`.

| Колонка | Тип | Описание |
|---|---|---|
| `klp_code` | TEXT | Код КЛП одной представительной позиции из схлопнутой группы (НЕ уникален как ключ, справочный) |
| `name_trade` | TEXT | Торговое название, **ВЕРХНИЙ РЕГИСТР**. Часть ключа уникальности записи |
| `standard_inn` | TEXT | МНН, **ВЕРХНИЙ РЕГИСТР** |
| `standard_form` | TEXT | Лекарственная форма (самый частый вариант в группе), ВЕРХНИЙ РЕГИСТР |
| `normalized_form` | TEXT | Нормализованная форма, ВЕРХНИЙ РЕГИСТР |
| `code_atc` | TEXT | Код АТХ. Часть ключа уникальности. **ВНИМАНИЕ**: может быть составным через `;`, например `"A01AB02;D08AX01"` — это означает комбинированный препарат с несколькими действующими веществами/кодами. Обязательно обрабатывать `split(';')` при использовании |
| `name_atc` | TEXT | Название по АТХ (самый частый вариант), ВЕРХНИЙ РЕГИСТР. Тоже может быть составным через `;`, синхронно с `code_atc` |
| `ftg_name_ru` | TEXT | Название фармгруппы на русском (самый частый вариант в группе) — то, ради чего всё затевалось |
| `actual` | TEXT | Строка `"true"` / `"false"` (НЕ булево значение SQLite), актуальна ли регистрация хотя бы одной из схлопнутых позиций |
| `source_rows_count` | INTEGER | Сколько исходных строк ЕСКЛП (упаковок/дозировок) схлопнулось в эту запись. Можно использовать как грубый индикатор "распространённости" препарата для сортировки в автокомплите (больше = более ходовой) |

### Критично важные особенности данных (учесть в коде!)

1. **Регистр**: все текстовые поля в БД приведены к верхнему регистру (`.strip().upper()`
   на этапе сборки, через Python — корректно для кириллицы). Родное отображение вида
   "Нурофен" в базе не хранится.

2. **SQLite `UPPER()`/`LOWER()` не работают с кириллицей** (ограничение движка, только
   ASCII). Это подтверждено экспериментально. **Нельзя** делать
   `WHERE UPPER(name_trade) = UPPER(?)` в SQL и рассчитывать на регистронезависимость —
   она не сработает для русских букв. Приводить пользовательский ввод к верхнему
   регистру нужно **в Dart** (`input.trim().toUpperCase()` — это работает корректно
   с юникодом), а сравнивать уже как точное совпадение по нормализованной строке.

3. **Ambiguity в `ftg_name_ru`**: у ~26% ATC-кодов (902 из 3534 в исходном полном
   справочнике `atc_ftg.db`) реально встречается несколько разных вариантов названия
   фармгруппы для одного кода — обычно это "сборные" коды типа "Прочие препараты"
   у комбинированных/нишевых средств. В `eskl_unique.db` для таких случаев уже выбран
   самый частый вариант, но 100% точность не гарантирована для таких кодов. Не критично
   для MVP, но если понадобится — есть отдельный файл `atc_ftg_conflicts.csv`
   с полным списком неоднозначных кодов и распределением вариантов.

4. **Дедупликация**: ключ уникальности — пара `(code_atc, name_trade)`. Одно и то же
   торговое название теоретически может встречаться с разными `code_atc`
   (пример из данных: "АРТРОКАМ" — с `M01AE01` и с составным `C01EB16;M01AE01` —
   это два реальных разных состава под одним брендом в разное время). Если код будет
   искать препарат по `name_trade` без учёта `code_atc`, может вернуться несколько строк.

## Принятые решения по неоднозначности (MVP-скоуп)

### Фильтрация по форме выпуска — только таблетки и капсулы

Для MVP `EsklRepository` должен фильтровать выдачу **только формами перорального
приёма** — таблетки и капсулы во всех их разновидностях (обычные, с оболочкой,
пролонгированные, жевательные, шипучие, для рассасывания, подъязычные и т.д.).
Капли, мази, гели, инъекции, свечи, вагинальные и прочие формы — исключаются.

Причина: под одним `name_trade` может встречаться несколько РАЗНЫХ по сути
препаратов (разные `code_atc`, разные показания) из-за разных путей введения
(см. пример "ДИКЛОФЕНАК" ниже) — сужение до одной категории форм резко снижает
количество настоящих неоднозначностей и делает MVP предсказуемым.

**Не** делать фильтрацию через `LIKE '%ТАБЛЕТ%' OR standard_form LIKE '%КАПСУЛ%'`
"в лоб" — под такой маской попадает мусор: вагинальные таблетки/капсулы, таблетки
"для приготовления глазных капель"/"для приготовления раствора" (полуфабрикат,
не для приёма внутрь), таблетки "для имплантации", "вспомогательное
вещество-капсулы желатиновые" (это пустые оболочки-сырьё, а не готовый препарат),
гомеопатические формы, ректальные.

Использовать явный список исключающих подстрок при фильтрации `standard_form`:

```dart
const excludeFormKeywords = [
  'ВАГИНАЛЬН',
  'ДЛЯ ПРИГОТОВЛЕНИЯ',
  'ДЛЯ ИМПЛАНТАЦИИ',
  'ВСПОМОГАТЕЛЬНОЕ ВЕЩЕСТВО',
  'ГОМЕОПАТИЧЕСК',
  'РЕКТАЛЬН',
];

bool isOralTabletOrCapsule(String standardForm) {
  final upper = standardForm.toUpperCase();
  final isTabletOrCapsule = upper.contains('ТАБЛЕТ') || upper.contains('КАПСУЛ');
  final isExcluded = excludeFormKeywords.any((kw) => upper.contains(kw));
  return isTabletOrCapsule && !isExcluded;
}
```

После такой фильтрации остаётся 79 конкретных вариантов `standard_form`
(из 100 исходных, содержащих "ТАБЛЕТ"/"КАПСУЛ").

**Пограничный случай, оставлен как есть, но стоит иметь в виду:**
`КАПСУЛЫ ДЛЯ ИНГАЛЯЦИЙ` / `С ПОРОШКОМ ДЛЯ ИНГАЛЯЦИЙ` формально проходят фильтр
(содержат "КАПСУЛ"), хотя по факту вставляются в ингалятор, а не проглатываются.
Оставлено сознательно на усмотрение будущей ревизии.

### Механизм 2 (шумовые дубли с одинаковой формой) — tie-break правило

Если после фильтрации по форме всё ещё остаётся несколько строк с одинаковыми
`(name_trade, standard_form)`, но разными `code_atc` — предпочтение отдаётся
записи, где `code_atc` **не составной** (не содержит `;`, то есть указан ровно
один код АТХ), а не комбинированному варианту. Если небазовых (не-`;`) вариантов
несколько — дальше выбирать по наибольшему `source_rows_count`.

```dart
// Псевдокод выбора среди кандидатов с одинаковыми (name_trade, standard_form)
EsklDrugEntry pickBest(List<EsklDrugEntry> candidates) {
  final singleCode = candidates.where((c) => !c.atcCodesRaw.contains(';')).toList();
  final pool = singleCode.isNotEmpty ? singleCode : candidates;
  pool.sort((a, b) => b.sourceRowsCount.compareTo(a.sourceRowsCount));
  return pool.first;
}
```

### Пример для понимания (ДИКЛОФЕНАК)

Под `name_trade = 'ДИКЛОФЕНАК'` в базе реально сосуществуют (до фильтрации формы):
ректальные свечи (`M01AB05`), гель наружный (`M02AA15`), глазные капли (`S01BC03`),
раствор для инъекций (составной код), таблетки кишечнорастворимые (составной код
`D11AX18;M01AB05`) и стоматологический гель с хлоргексидином (`A01AD11`,
совсем другая ФТГ). После фильтрации "только таблетки/капсулы" останется только
одна форма — таблетки, а внутри неё tie-break по одиночному ATC-коду уберёт
"шумовой" составной вариант `D11AX18;M01AB05` в пользу чистого `M01AB05`.
